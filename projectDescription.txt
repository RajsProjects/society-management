1. SYSTEM OVERVIEW & ARCHITECTURAL FOUNDATION
====================================================================================================
CivicLink (branded as "Samaaj" on the client interface) is an enterprise-grade, multi-tenant 
Software-as-a-Service (SaaS) platform engineered for residential housing societies, gated 
communities, and Resident Welfare Associations (RWAs).

The platform addresses core operational hurdles in community management:
  - Transparent Maintenance Billing & Bank Reconciliation (UPI anti-fraud duplicate checks)
  - Democratic Resident Voting & Capital Improvement Proposal Tracking
  - Real-time Issue & Complaint Ticketing with SLA Workflows
  - Secure Resident Onboarding via Verification & Tokenized Invitations
  - Broadcast Emergency Alerts & Targeted Community Announcements
  - Automated SaaS Subscription Billing via Razorpay Webhooks
  - Complete Tenant Isolation with zero-knowledge data protection between neighboring societies

Architectural Philosophy:
  - Shared Database, Shared Collection Multi-Tenancy with Discriminator Pattern (`societyId`).
  - Transparent Data Filtering: Repositories and queries are intercepted at the persistence 
    engine layer (`MultiTenantMongoTemplate`), ensuring application code cannot accidentally leak 
    data across tenants.
  - Dual-Scope Platform Isolation: Complete architectural decoupling between Global Platform 
    Administrators and Domestic Society Tenants.
  - High Concurrency: Built on Java 21 Virtual Threads (`Loom`), enabling non-blocking execution 
    of thousands of parallel I/O requests (database reads, emails, AWS S3 uploads, Redis calls).

3. ENTERPRISE MULTI-TENANCY & ZERO-KNOWLEDGE DATA ISOLATION ENGINE
====================================================================================================
Every society registered on CivicLink represents an independent tenant. All domestic records 
(users, flats, bills, complaints, issues, announcements, votes, subscriptions) are partitioned 
by a mandatory `societyId`.

Key Components:

A. TenantContext:
   - Holds the current request's `societyId` in a thread-safe `ThreadLocal<String>`.
   - Populated early in the request lifecycle by `JwtAuthenticationFilter` after decoding the JWT.
   - Cleared unconditionally in a `finally` block before the thread returns to the thread pool:
     `TenantContext.clear();`
   - Provides functional execution wrappers: `TenantContext.runAsTenant(societyId, runnable)` and
     `TenantContext.callAsTenant(societyId, callable)` for scheduled tasks and system workers.

B. MultiTenantMongoTemplate:
   - Custom implementation extending Spring Data's `MongoTemplate`.
   - Intercepts all database operations:
     * Reads: `find`, `findById`, `findOne`, `findAndModify`, `findAndRemove`, `count`, `exists`
     * Writes/Mutations: `save`, `insert`, `insertAll`, `remove`, `updateFirst`, `updateMulti`
     * Analytics: `aggregate`, `aggregate(TypedAggregation)`
   - How it works:
     1. Checks if the target collection is tenant-scoped. (The `societies` collection is exempt).
     2. Checks if the caller has `ROLE_PLATFORM_ADMIN`. (Platform admins manage societies globally).
     3. For normal requests, retrieves `TenantContext.getSocietyId()`.
     4. On Queries: Inspects the incoming `Query` object. If `societyId` is already present, verifies
        it matches the authenticated tenant; if it mismatches or uses prohibited operators, throws 
        `AccessDeniedException` immediately. If omitted, automatically appends:
        `Criteria.where("societyId").is(tenantId)`.
     5. On Writes: Inspects the entity via reflection. If `societyId` is null, automatically stamps
        the active tenant ID. If the entity already has a different `societyId`, throws 
        `AccessDeniedException` to prevent cross-tenant object overwrites.
     6. Field Reflection Cache: Utilizes a static `ConcurrentHashMap<Class<?>, Field>` with a 
        `NO_TENANT_FIELD` sentinel for O(1) reflection resolution without repeated reflection overhead.
     7. Aggregation Pipeline Rewriting: Automatically injects a `$match: { societyId: tenantId }` 
        stage at the front of the pipeline and verifies any `$lookup` sub-pipelines.

4. SECURITY, CRYPTOGRAPHY & DUAL-SCOPE ACCESS CONTROL
====================================================================================================
A. Double-Hashed Password Storage (BCrypt + Secret Pepper):
   - Handled by `PepperedPasswordEncoder`.
   - Formula: `BCrypt.hash(rawPassword + serverPepper, strength = 10)`.
   - Even if the database is compromised, passwords cannot be cracked with rainbow tables without 
     the high-entropy server-side pepper secret stored outside the database.

B. Dual-Scope Isolation Architecture:
   - Platform Scope:
     * Role: `ROLE_PLATFORM_ADMIN`
     * Scope: Global system infrastructure, society registration approvals, JVM health, broadcasts.
     * Restriction: Zero domestic tenant access. Platform admins cannot view or manipulate 
       neighboring societies' private ledgers, resident complaints, or chat messages.
   - Domestic Society Scope:
     * Roles: `SUPER_ADMIN` > `ADMIN` > `RESIDENT` (organized via Spring Security `RoleHierarchyImpl`).
     * `SUPER_ADMIN`: Society creator / President. Full administrative authority over their society.
     * `ADMIN`: Committee member / Manager. Can manage residents, flats, complaints, bills, notices.
     * `RESIDENT`: Apartment owner or tenant. Can view own bills, submit complaints, vote on issues.

C. High-Performance Stateless JWT Engine:
   - Secret key and `JwtParser` pre-initialized in `@PostConstruct` in `JwtService`.
   - Single-Pass Extraction: Token claims are parsed and cryptographically validated exactly ONCE per 
     request in `JwtAuthenticationFilter` via `jwtService.parseAndValidateClaims(token)`.
   - Token payload claims: `sub` (email), `userId`, `role`, `platformRole`, `status`, `societyId`, `exp`.

5.1 AuthService (`com.Application.SocietyManagement.users.service.AuthService`)
----------------------------------------------------------------------------------------------------
- WHAT IT DOES:
  Manages public user onboarding (resident registration) and authentication (login).
- HOW IT WORKS:
  1. Signup (`signup(SignupRequest request)`):
     - Validates email uniqueness across all users (`userRepository.findByEmail`).
     - Resolves society identity: The resident must supply a valid `joinCode` (e.g. `SOC-KD8X72`).
     - Looks up society by join code. Verifies society exists and status is `ACTIVE`.
     - Hashes password using `PepperedPasswordEncoder`.
     - Constructs `User` entity with `role = RESIDENT` and `status = PENDING`.
     - Saves user in MongoDB. The account remains in `PENDING` status until a society admin approves it.
  2. Login (`login(LoginRequest request)`):
     - Fetches user by email. Throws HTTP 401 if not found.
     - Compares submitted password against stored BCrypt hash using `passwordEncoder.matches`.
     - Enforces status verification:
       * `PENDING` -> Throws HTTP 403 ("Account pending admin approval").
       * `INACTIVE` -> Throws HTTP 403 ("Account is inactive").
       * `BLOCKED` -> Throws HTTP 403 ("Account has been blocked").
     - If `ACTIVE`, generates JWT token signed with HMAC-SHA256 containing user metadata.
     - Returns `AuthResponse` containing Bearer token, roles, user name, and societyId.

5.2 UserService (`com.Application.SocietyManagement.users.service.UserService`)
----------------------------------------------------------------------------------------------------
- WHAT IT DOES:
  Handles resident account lifecycle management, status approvals/rejections, member directory 
  queries, and password changes.
- HOW IT WORKS:
  1. Status Update (`updateStatus(String userId, Status status)`):
     - Enforces active tenant context (`TenantContext.getSocietyId()`).
     - Fetches target user within the tenant (`findByIdAndSocietyId`).
     - Privilege Protection Rule: Prevents modifying accounts with role `ADMIN` or `SUPER_ADMIN`.
       An admin cannot demote or block another admin through this endpoint.
     - Updates status (`ACTIVE`, `INACTIVE`, `BLOCKED`) and saves.
  2. Paginated User Listing (`getUsers(...)`):
     - Supports multi-attribute filtering by `status` and `role`.
     - Sorts by creation timestamp descending (`createdAt DESC`).
     - Maps results to token-efficient `UserSummarydto` records.
  3. Profile Retrieval (`getCurrentUser`, `getUserByEmail`):
     - Returns authenticated user details and permissions.
  4. Password Change (`changePassword(...)`):
     - Verifies `currentPassword` against current user hash using BCrypt pepper.
     - Hashes `newPassword` and saves updated user.

5.3 InviteService (`com.Application.SocietyManagement.users.service.InviteService`)
----------------------------------------------------------------------------------------------------
- WHAT IT DOES:
  Enables society administrators to invite residents and staff via secure, time-limited invitation 
  tokens delivered through asynchronous email.
- HOW IT WORKS:
  1. Sending Invitation (`invite(...)`):
     - Validates tenant context and caller role.
     - Privilege Escalation Guard:
       * An `ADMIN` cannot invite an `ADMIN` or `SUPER_ADMIN`.
       * A `SUPER_ADMIN` cannot invite another `SUPER_ADMIN`.
     - Checks that the recipient email is not already registered as a user.
     - Checks that no unused pending invite already exists for that email in the society.
     - Generates a cryptographically random UUID token.
     - Saves an `InviteToken` document with `expiresAt = Instant.now() + 48 Hours` and `used = false`.
     - Asynchronously calls `EmailService.sendInviteEmail` with the invitation link.
  2. Accepting Invitation (`acceptInvite(AcceptInviteRequest request)`):
     - Looks up token in MongoDB. Throws HTTP 404 if invalid.
     - Verifies token is not already used (`invite.isUsed() == false`) and not expired.
     - Confirms email is still available.
     - Creates `User` entity directly with `status = ACTIVE` (since the invitation was pre-authorized 
       by an administrator), assigning the invited role and flatId.
     - Marks `InviteToken.used = true` and saves.
     - Generates an immediate JWT session token for seamless login.
  3. Scheduled Token Cleanup (`cleanupExpiredTokens()`):
     - Runs every hour (`@Scheduled(cron = "0 0 * * * *")`).
     - Executes bulk deletion: `inviteTokenRepository.deleteByExpiresAtBefore(Instant.now())`.

5.4 CustomUserDetailsService (`com.Application.SocietyManagement.users.service.CustomUserDetailsService`)
----------------------------------------------------------------------------------------------------
- WHAT IT DOES:
  Implements Spring Security's `UserDetailsService` contract to load user principals during JWT 
  authentication filtering.
- HOW IT WORKS:
  - High-Speed In-Memory Cache: Houses a `ConcurrentHashMap<String, CachedUser>` with a 60-second TTL.
  - On `loadUserByUsername(email)`:
    * Checks if the user is present in memory and not expired. If so, returns cached `UserDetails` in O(1) 
      without database round-trips.
    * If miss or expired, queries `userRepository.findByEmail(email)`.
    * Caches user details for 60 seconds.
  - Provides `evictUser(email)` for cache invalidation upon credential changes.

5.5 JwtService (`com.Application.SocietyManagement.users.service.JwtService`)
----------------------------------------------------------------------------------------------------
- WHAT IT DOES:
  Generates, cryptographically verifies, and extracts claims from HMAC-SHA256 JWT tokens.
- HOW IT WORKS:
  - Startup Initialization (`@PostConstruct`): Validates secret length (minimum 256 bits) and compiles 
    the thread-safe `SecretKey` and `JwtParser` instance once.
  - Token Generation (`generateToken(User user)`):
    * Encodes subject (email), `userId`, `role`, `platformRole`, `status`, and `societyId`.
    * Sets issue time and expiration (configured via `jwt.expiration`, default 24 hours).
    * Signs with HMAC-SHA256.
  - Single-Pass Validation (`parseAndValidateClaims(String token)`):
    * Executes a single cryptographic parse using the pre-built parser.
    * Returns the `Claims` payload or `null` if expired/tampered, eliminating duplicate verification passes.

5.6 SocietyService (`com.Application.SocietyManagement.society.service.SocietyService`)
----------------------------------------------------------------------------------------------------
- WHAT IT DOES:
  Oversees society registration, document uploads to AWS S3, platform approval workflows, join code 
  generation, and tenant profile retrieval.
- HOW IT WORKS:
  1. Society Registration (`register(...)`):
     - Public endpoint. Verifies uniqueness of registration number and administrator email.
     - File Upload: If registration certificate/document is uploaded, validates file size (<= 5MB) 
       and MIME type (PDF, JPEG, PNG). Streams bytes to S3 bucket in folder `society-documents/` 
       via `S3Service.uploadFile`.
     - Generates a permanent unique alphanumeric join code via `JoinCodeGenerator` (e.g. `SOC-8F9K2L`).
     - Creates `Society` entity with `status = PENDING_VERIFICATION` and plan `TRIAL`.
     - Creates the initial `SUPER_ADMIN` user in `PENDING` status.
     - Links `superAdminId` to the society and persists both records.
  2. Platform Verification (`verify(...)`):
     - Restricted to `ROLE_PLATFORM_ADMIN`.
     - If rejected: Sets `status = REJECTED` and records mandatory `rejectionReason`.
     - If approved: Sets `status = ACTIVE`, records `verifiedAt` and `verifiedBy`, initializes 14-day 
       trial window (`trialEndsAt = now + 14 days`), and immediately transitions the society's 
       `SUPER_ADMIN` user account to `ACTIVE` so they can log in.
  3. Public Join Lookup (`getByJoinCode(joinCode)`):
     - Resolves society public profile for registration links. Confirms society is active.
  4. Profile Caching (`getMySociety()`):
     - Caches society metadata in an in-memory concurrent map with a 30-second TTL to reduce 
       repetitive reads on tenant dashboards.
  5. S3 Presigned URL (`getDocumentUrl(societyId)`):
     - Generates a secure, time-expiring AWS S3 presigned GET URL for reviewing registration certificates.

5.9 MaintenanceBillService (`com.Application.SocietyManagement.finance.service.MaintenanceBillService`)
----------------------------------------------------------------------------------------------------
- WHAT IT DOES:
  Automates society maintenance billing, resident payments, financial reconciliation, and overdue 
  enforcement.
- HOW IT WORKS:
  1. Bill Generation (`createBill(CreateBillRequest request)`):
     - Restricted to `ADMIN` / `SUPER_ADMIN`.
     - Validates that the target user belongs to the current society and matches the flat ID.
     - Uniqueness Check: Ensures no duplicate bill exists for the same apartment in the same billing 
       month (`existsByApartmentNumberAndBillingMonthAndSocietyId`).
     - Persists `MaintenanceBill` with status `PENDING`.
     - Event Publishing: Publishes `BillGeneratedEvent` via Spring's `ApplicationEventPublisher`. 
       `EmailService` listens asynchronously and dispatches the HTML invoice email without blocking 
       the HTTP response.
  2. Role-Based Bill Queries (`getBills(...)`):
     - Admins can view all bills across the society, filterable by status (`PENDING`, `PAID`, `OVERDUE`).
     - Residents can only see bills assigned to their own `userId`.
  3. Payment Submission with Anti-Fraud Checks (`payBill(...)`):
     - Validates resident ownership of the bill.
     - Rejects if bill is already `PAID` or `PENDING_VERIFICATION`.
     - Validates full payment (partial amounts rejected).
     - UPI Transaction Regex Validation: Validates format against alphanumeric pattern (`^[A-Za-z0-9_-]{10,50}$`).
     - Anti-Fraud Cross-Bill Uniqueness: Checks `billRepository.existsByUpiTransactionId(txnId)` across 
       all bills to prevent recycling the same bank transaction reference for multiple payments.
     - Concurrency Control: Acquires a Redis distributed lock (`bill:pay:{billId}`) for 15 seconds to 
       prevent double-submission race conditions.
     - Transitions status to `PENDING_VERIFICATION` and stores `upiTransactionId`.
  4. Payment Reconciliation (`verifyPayment`, `rejectPayment`):
     - Admin/Accountant reviews bank account statement.
     - On Verify: Sets status to `PAID`, stamps `paidAt = Instant.now()`, and publishes `PaymentSuccessEvent` 
       which asynchronously triggers payment receipt email dispatch.
     - On Reject: Clears `upiTransactionId` and reverts status to `PENDING` (or `OVERDUE` if past due date).
  5. Daily Overdue Automation (`markOverdueBills()`):
     - Scheduled daily at midnight UTC (`@Scheduled(cron = "0 0 0 * * *", zone = "UTC")`).
     - Acquires Redis distributed lock `dist_lock:markOverdueBills` to ensure only ONE node in a clustered 
       deployment executes the batch.
     - Executes an atomic MongoDB `updateMulti`:
       Target: `{ status: 'PENDING', dueDate: { $lt: today } }`
       Update: `{ $set: { status: 'OVERDUE', updatedAt: now } }`.

5.10 SubscriptionService (`com.Application.SocietyManagement.subscription.service.SubscriptionService`)
----------------------------------------------------------------------------------------------------
- WHAT IT DOES:
  Manages society SaaS subscription plans (`BASIC`, `GROWTH`, `SCALE`), Razorpay payment orders, and 
  automated plan activation.
- HOW IT WORKS:
  1. Order Creation (`createOrder(SubscriptionPlan plan)`):
     - Looks up plan price from `PlanPricingConfig` (e.g. Basic: ₹999/mo, Growth: ₹2,499/mo, Scale: ₹4,999/mo).
     - Communicates with Razorpay API using `RazorpayClient` to create an order in INR currency.
     - (In test/mock mode with dummy credentials, generates mock order IDs).
     - Persists a `Subscription` record with `paymentStatus = PENDING`.
     - Returns `OrderResponse` with `razorpayOrderId`, amount, and client `keyId`.
  2. Client-Side Payment Verification (`verifyPayment(...)`):
     - Validates HMAC-SHA256 signature using `Utils.verifyPaymentSignature(...)` with Razorpay key secret.
     - If signature matches, invokes `activateSubscription(...)`.
  3. Idempotent Activation (`activateSubscription(...)`):
     - Shared by client verification endpoint and asynchronous webhooks.
     - If `subscription.paymentStatus == SUCCESS`, no-ops immediately to prevent race conditions.
     - Marks subscription `SUCCESS`, sets `startDate = now` and `endDate = now + 30 days`.
     - Updates `Society` entity: `plan = subscription.plan`, `subscriptionStatus = ACTIVE`, 
       `subscriptionEndsAt = endDate`.
  4. Plan Changes (`changePlan(...)`):
     - Validates society is active and not already on the requested plan. Reuses order creation pipeline.

----------------------------------------------------------------------------------------------------
- WHAT IT DOES:
  Processes server-to-server webhook events from Razorpay for robust, asynchronous payment settlement.
- HOW IT WORKS:

----------------------------------------------------------------------------------------------------
- WHAT IT DOES:
  Automated background daemon monitoring trial periods and active subscription expirations.
- HOW IT WORKS:

  - Combined with `SubscriptionEnforcementFilter`, automatically locks out mutation operations 
    until renewal while keeping data readable.

5.14 IssueService (`com.Application.SocietyManagement.issue.service.IssueService`)
----------------------------------------------------------------------------------------------------
- WHAT IT DOES:
  Powers community democracy, collective decision making, and capital expenditure proposals 
  (e.g., rooftop solar installations, EV charging bays, CCTV upgrades).
- HOW IT WORKS:
  1. Issue Submission (`createIssue(...)`):
     - Residents or admins post a proposal with title, description, optional photo URL, and priority.
     - Stored with `status = OPEN`.
  2. Anti-Duplicate Democratic Voting (`addVote`, `removeVote`):
     - Rule: A user cannot vote on their own proposal (`creatorId != userId`).
     - Rule: A user can only vote once per issue. Enforced by unique compound index on `IssueVote`:
       `{'issueId': 1, 'userId': 1}` with uniqueness constraint.
     - Throws HTTP 409 if already voted.
     - `removeVote` allows withdrawing a vote, deleting the `IssueVote` document.
  3. High-Performance Bulk Vote Tallying (Eliminating N+1 Queries):
     - When listing issues, avoids querying vote counts one-by-one.
     - Executes a single aggregated MongoDB query: `issueVoteRepository.countVotesByIssueIds(issueIds)` 
       using `$match: { issueId: { $in: ... } }` and `$group: { _id: "$issueId", count: { $sum: 1 } }`.
     - Assembles responses in O(N) memory, with an automated fallback if aggregation encounters errors.
  4. Sorting:
     - Supports dynamic sorting by `createdAt` or by democratic popularity (`voteCount DESC`).

5.15 AnnouncementService (`com.Application.SocietyManagement.communication.service.AnnouncementService`)

5.16 EmailService (`com.Application.SocietyManagement.communication.email.service.EmailService`)
----------------------------------------------------------------------------------------------------
- WHAT IT DOES:
  Event-driven asynchronous email notification system for invitations, invoices, payment receipts, 
  and automated payment reminders.
- HOW IT WORKS:
  1. Event Bus Integration:
     - `@Async @EventListener handleBillGenerated(BillGeneratedEvent event)`: Listens for newly created 
       bills and renders `email/bill-generated.html` template.
     - `@Async @EventListener handlePaymentSuccess(PaymentSuccessEvent event)`: Listens for approved 
       payments and renders `email/payment-success.html` receipt.
  2. Scheduled Reminders:
     - 3-Day Due Date Reminder: Runs daily at 9:00 AM UTC (`@Scheduled(cron = "0 0 9 * * *", zone = "UTC")`). 
       Finds `PENDING` bills where `dueDate == today + 3 days` and notifies residents.
     - Overdue Notification: Runs daily at 9:00 AM UTC. Finds `OVERDUE` bills and delivers urgent alerts.
  3. Clustered Concurrency: Uses `DistributedLockService.tryLock(...)` for 15 minutes to guarantee only 
     one server instance in a multi-pod Kubernetes cluster sends out reminder batches.
  4. Thymeleaf HTML Rendering: Populates dynamic variables (resident name, amount, month, invoice links).
  5. Resilient Mock Delivery: In local/dev environments without SMTP credentials, logs the message 
     safely without crashing.

5.17 DashboardController (`com.Application.SocietyManagement.dashboard.controller.DashboardController`)
----------------------------------------------------------------------------------------------------
- WHAT IT DOES:
  Aggregates management dashboard analytics across all modules in real time.
- HOW IT WORKS:
  - Parallel Virtual Thread Fan-Out:
    Fires 12 concurrent `CompletableFuture` queries simultaneously via `taskExecutor` (Virtual Threads):
      1. `totalResidents`
      2. `pendingApprovals`
      3. `totalFlats`
      4. `occupiedFlats`
      5. `openComplaints`
      6. `inProgressComplaints`
      7. `resolvedComplaints`
      8. `totalBills`
      9. `paidBills`
      10. `overdueBills`
      11. `openIssues`
      12. `resolvedIssues`
  - Joins all queries concurrently using `CompletableFuture.allOf(...)`. Total latency equals the duration 
    of the single slowest query, rather than the sum of 12 sequential queries.
  - 10-Second Concurrent In-Memory Cache: Stores `CachedDashboardStats` per `societyId` to protect MongoDB 
    from dashboard refresh spam.

5.18 DistributedLockService (`com.Application.SocietyManagement.core.util.DistributedLockService`)
----------------------------------------------------------------------------------------------------
- WHAT IT DOES:
  Provides distributed mutex locks using Redis to coordinate scheduled tasks across clustered backend instances.
- HOW IT WORKS:
  - Calls `redisTemplate.opsForValue().setIfAbsent("dist_lock:" + lockName, "locked", duration)`.
  - Returns `true` if lock was acquired, `false` if another instance is already processing.
  - Safe Fallback: If Redis is temporarily unreachable or disabled, allows execution with a warning.

6. FILTERS & PIPELINE MIDDLEWARE
====================================================================================================
The HTTP request pipeline executes through the following filters in order:

1. RequestLoggingFilter:
   - Assigns a unique trace ID (`X-Trace-Id`) to every request.
   - Logs method, URI, client IP, and execution time in milliseconds.

2. RateLimitingFilter (Positioned before UsernamePasswordAuthenticationFilter):
   - Sliding-window rate limiter powered by Redis.
   - Intercepts sensitive routes: `/api/v1/auth/*`, `/api/v1/societies/register`, `/api/v1/societies/join/*`, 
     `/api/v1/users/change-password`, `/api/v1/communication/email/test`, `/api/v1/subscriptions/create-order`.
   - Rate limit: Configurable (default 120 requests per minute per IP).
   - Atomic increment via `redisTemplate.opsForValue().increment(key)`. Sets Redis TTL on first request (`count == 1`).
   - Returns HTTP 429 ("Too many requests") if limit is exceeded.
   - Uses `request.getRemoteAddr()` aligned with Spring's forward-headers strategy to prevent header spoofing.

3. JwtAuthenticationFilter:
   - Reads `Authorization: Bearer <token>` header.
   - Performs single-pass cryptographic parse using pre-compiled parser in `JwtService`.
   - Loads user details via cached `CustomUserDetailsService`.
   - Checks account status: rejects if `PENDING`, `INACTIVE`, or `BLOCKED` with HTTP 403.
   - Injects `UsernamePasswordAuthenticationToken` into Spring Security's `SecurityContextHolder`.
   - Injects `societyId` into `TenantContext`.
   - Guarantees `TenantContext.clear()` in a `finally` block after the downstream chain completes.

4. SubscriptionEnforcementFilter (Positioned after JwtAuthenticationFilter):
   - Checks HTTP method: skips GET/HEAD/OPTIONS (read operations remain accessible).
   - Skips allowed renewal endpoints (`/api/v1/subscriptions/*`, `/api/v1/webhooks/*`, `/api/v1/auth/*`).
   - Skips platform administrators (`ROLE_PLATFORM_ADMIN`).
   - Evaluates society status:
     * If society is inactive or suspended: Returns HTTP 403.
     * If society subscription is `EXPIRED` or `PAST_DUE`: Returns HTTP 402 ("Payment Required") 
       with notice that renewal is required to make mutations.

10. PERFORMANCE OPTIMIZATIONS, CONCURRENCY & OBSERVABILITY
====================================================================================================
Recent High-Impact Optimizations Applied:
  1. Single-Pass JWT Validation: Pre-cached `SecretKey` and `JwtParser` in `JwtService` eliminates 
     2-3 repetitive parsing and cryptographic signature checks per request.
  2. Redis Rate Limiter O(1) Expiry: Removed redundant `redisTemplate.getExpire()` calls; sets 60-second 
     TTL exclusively on initial key generation (`count == 1L`).
  3. MultiTenantMongoTemplate Reflection Cache: Implemented `NO_TENANT_FIELD` sentinel in 
     `TENANT_FIELD_CACHE`, converting negative field lookups from expensive repeated reflection 
     hierarchy traversals to instant O(1) map hits.
  4. SecurityConfig ObjectMapper Reuse: Replaced ad-hoc `new ObjectMapper()` allocations inside 
     authentication error handlers with a static shared singleton.
  5. UserDetailsService In-Memory Caching: 60-second concurrent in-memory caching eliminates redundant 
     MongoDB hits during burst requests from authenticated clients.
  6. Dashboard Parallel Query Fan-Out: Executes 12 MongoDB counts concurrently using Project Loom 
     Virtual Threads and `CompletableFuture.allOf(...)`, combined with a 10-second per-society cache.
  7. Redis Connection Pooling: Configured Lettuce asynchronous connection pool with `commons-pool2` 
     (max-active: 64, max-idle: 16, min-idle: 4).
  8. Observability & Telemetry: Integrated Spring Boot Actuator with Prometheus scraping 
     (`/actuator/prometheus`) and pre-built Grafana dashboards monitoring JVM heap, virtual thread 
     pinning, HTTP request latencies, and MongoDB connection metrics.
